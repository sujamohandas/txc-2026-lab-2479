  • Use Bob (IBM AI) to generate Terraform code using IBM-certified modules from the terraform-ibm-modules registry

Phase 3 — Review the Code (Vault Integration)

4

How the IBM Cloud API Key Is Secured

The API key is never written as plain text anywhere. The secure flow is:

Security Flow HCP Vault kv/IBM_CLOUD_API_KEY → data "vault_kv_secret_v2" in vault.tf → provider "ibm" { ibmcloud_api_key = … } in providers.tf

vault.tf — reads the secret from Vault at plan/apply time:

data "vault_kv_secret_v2" "ibmcloud" {
  mount = "kv"
  name  = "IBM_CLOUD_API_KEY"
}

providers.tf — the IBM provider receives the value directly:

provider "ibm" {
  ibmcloud_api_key = data.vault_kv_secret_v2.ibmcloud.data["IBM_KEY"]
  region           = var.region
}
State file sensitivity A data source writes values to Terraform state. Restrict access to your HCP Terraform workspace state and treat it as sensitive.

Task 2Break, Diagnose & Self-Heal with IBM Bob

What this task validates The same Bob + MCP setup used to build the environment can also maintain it. You will deliberately break the infrastructure, watch Bob detect the configuration drift via terraform plan, and then approve a self-healing terraform apply to restore service — all without touching the IBM Cloud console.

5.1 — Breaking the Environment

B

Run the Break Script

The provided script break-lab-app.sh (or equivalent PowerShell) performs two changes on the VSI security group demo-vsi-sg:

  1. Deletes the inbound rule that allows TCP port 80
  2. Adds a replacement inbound rule for TCP port 8080

Nginx inside the VSI is untouched — it still listens on port 80. Only the network path is broken.

# PowerShell equivalent of break-lab-app.sh
$sgId     = "<your-vsi-sg-id>"            # e.g. r006-40b33d67-...
$rule80Id = "<port-80-rule-id>"           # e.g. r006-4c09a388-...

# 1. Delete port 80 inbound rule
Invoke-RestMethod -Uri "https://us-south.iaas.cloud.ibm.com/v1/security_groups/$sgId/rules/$rule80Id?version=2024-01-01&generation=2" `
  -Method DELETE -Headers @{ "Authorization" = "Bearer $iamToken" }

# 2. Add port 8080 inbound rule
Invoke-RestMethod -Uri "https://us-south.iaas.cloud.ibm.com/v1/security_groups/$sgId/rules?version=2024-01-01&generation=2" `
  -Method POST `
  -Headers @{ "Authorization" = "Bearer $iamToken"; "Content-Type" = "application/json" } `
  -Body '{"direction":"inbound","protocol":"tcp","port_min":8080,"port_max":8080,"remote":{"cidr_block":"0.0.0.0/0"}}'

After running the script, the security group rules are:

inboundtcp8080⚠️ Added (wrong port)

outboundall—✅ Unchanged

The plan output will show exactly one drift event and one remediation action:

Terraform will perform the following actions:

# module.vsi.ibm_is_security_group_rule.security_group_rules["demo-vsi-sg-allow-http"] will be created
+ resource "ibm_is_security_group_rule" "security_group_rules" {
+ direction = "inbound"
+ group = "r006-40b33d67-d293-46d1-8826-bd6768906bfc"

+ port_max = 80
+ remote = "0.0.0.0/0"

Plan: 1 to add, 0 to change, 0 to destroy.

Bob's Root Cause Explanation

Root Cause Identified Terraform detected configuration drift on the VSI security group demo-vsi-sg. The inbound rule allowing TCP port 80 from 0.0.0.0/0 — defined in main.tf as allow-http — was deleted from IBM Cloud outside of Terraform (by the break script). A rogue rule for port 8080 was added in its place.

Because Nginx listens on port 80, and the ALB pool health check targets port 80, the load balancer can no longer reach the instance. All traffic is dropped — causing the app to appear unreachable.

The rogue port 8080 rule is irrelevant; nothing in the stack uses port 8080.
Key insight Terraform only manages what is declared in code. The orphaned port 8080 rule was added out-of-band — Terraform will not remove it (unless you explicitly set incremental_rule_update = false). It reports 1 to add (the missing port 80 rule) but leaves unmanaged rules alone.
